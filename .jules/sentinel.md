## 2026-04-12 - Fix eval command injection in deploy script
**Vulnerability:** The deployment script `deploy_to_brain.sh` contained an unsafe `eval` statement designed to expand the tilde (`~`) character when evaluating user input for a directory path: `eval LOCAL_DIR="$LOCAL_DIR"`. This introduced a critical command injection vulnerability. A malicious actor could provide input like `"; ls -al; echo "` to execute arbitrary commands with the privileges of the script user.
**Learning:** Shell scripts processing user input should avoid the `eval` builtin wherever possible as it evaluates arbitrary code. While `eval` is often tempting for tasks like tilde expansion, safer alternatives exist in bash.
**Prevention:** Rather than utilizing `eval`, use safe bash parameter expansion constructs. In this case, `LOCAL_DIR="${LOCAL_DIR/#\~/$HOME}"` performs a simple pattern substitution, replacing a leading tilde with the user's home directory path without executing the input as a command.
## 2026-04-13 - Fail-Secure Authentication for Diagnostic Endpoints
**Vulnerability:** The `/health` and `/debug/sentry-test` diagnostic endpoints were unauthenticated. If internal details (such as project IDs, model names, environment statuses) are leaked or diagnostic crashes can be externally triggered, it could assist attackers in reconnaissance or cause a Denial of Service.
**Learning:** Endpoints exposing sensitive configuration or backend metadata must implement application-level authentication. Furthermore, authentication dependencies must be fail-secure: if the server's expected API key environment variable is not configured, it should raise a generic 500 error instead of failing open or leaking the misconfiguration details to the client.
**Prevention:** Implement `verify_admin_key` using `fastapi.security.APIKeyHeader` and `secrets.compare_digest` for such endpoints. Always check for the presence of the expected configuration and raise an internal server error if it's missing, avoiding the assumption that network boundaries alone provide sufficient security.
## 2026-04-13 - Secure Diagnostic Endpoints While Preserving Infrastructure
**Vulnerability:** The `/health` endpoint previously exposed sensitive internal backend state (project IDs, models, database connection details). Attempting to secure it by placing an authentication layer over the entire `/health` path would inadvertently block health probes used by container orchestration and load balancers, causing a denial of service (un-deployable state).
**Learning:** Public health endpoints must remain unauthenticated for infrastructure compatibility but should only return minimal, non-sensitive liveness indicators (e.g., `{"status": "ok"}`). Sensitive diagnostic and debugging metadata must be moved to a separate, authenticated endpoint. Furthermore, authentication dependencies on sensitive endpoints should be fail-secure—if an expected configuration or key is absent on the server, the endpoint must fail with a generic 500 error instead of failing open.
**Prevention:** Separate concerns: keep `/health` simple and public. Create a dedicated `/admin/info` endpoint secured via `verify_admin_key` using `fastapi.security.APIKeyHeader` and `secrets.compare_digest` for diagnostic details.
