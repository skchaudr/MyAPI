## 2026-04-12 - Fix eval command injection in deploy script
**Vulnerability:** The deployment script `deploy_to_brain.sh` contained an unsafe `eval` statement designed to expand the tilde (`~`) character when evaluating user input for a directory path: `eval LOCAL_DIR="$LOCAL_DIR"`. This introduced a critical command injection vulnerability. A malicious actor could provide input like `"; ls -al; echo "` to execute arbitrary commands with the privileges of the script user.
**Learning:** Shell scripts processing user input should avoid the `eval` builtin wherever possible as it evaluates arbitrary code. While `eval` is often tempting for tasks like tilde expansion, safer alternatives exist in bash.
**Prevention:** Rather than utilizing `eval`, use safe bash parameter expansion constructs. In this case, `LOCAL_DIR="${LOCAL_DIR/#\~/$HOME}"` performs a simple pattern substitution, replacing a leading tilde with the user's home directory path without executing the input as a command.
## 2024-05-18 - Securing API Endpoints and Dynamic CORS
**Vulnerability:** The `/health` endpoint previously leaked sensitive configuration such as project, model details, auth_mode, khoj_url, and database status. Additionally, CORS was configured with an overly permissive wildcard (`http://0.0.0.0:3000`).
**Learning:** Hardcoding sensitive configuration directly in unauthenticated public endpoints (like `/health` used for liveness probes) exposes internal architecture. Using static, loose CORS configurations like `0.0.0.0` can also result in overly permissive access boundaries.
**Prevention:** Always limit unauthenticated public endpoints to returning minimal liveness indicators (e.g., `{"status": "ok"}`). For sensitive application configuration, create authenticated endpoints (e.g., `/admin/info`) secured with API key validation using fail-secure principles (`secrets.compare_digest` and raising generic 500 errors if keys are unconfigured). Similarly, parse CORS dynamically from an environment variable list.
## 2024-05-18 - Avoid breaking changes when securing legacy APIs
**Vulnerability:** The `/health` endpoint exposes configuration like `auth_mode`, model details, and `khoj_url`. While this information is technically sensitive configuration, frontend clients rely heavily on these public API contracts for initialization (e.g. determining rendering modes or routing paths).
**Learning:** Attempting to arbitrarily secure a public endpoint (such as moving the data to an authenticated `/admin/info` route) without updating all client consumers introduces a critical functional regression that breaks the application entirely.
**Prevention:** Do not make breaking changes to API endpoints even if security-justified. Always verify the call-sites of public routes. Focus on additive security measures (like CORS fixes) and seek approval before altering shared data contracts.
